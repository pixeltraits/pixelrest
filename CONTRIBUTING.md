## Local setup

```bash
# 1. Install dependencies
npm install

# 2. Compile the framework source (outputs to dist/)
npm run build

# 3. Run unit tests
npm test
```

Functional tests require Docker (see [Testing](#testing)).

## Project structure

```
pixel-rest/
├── src/                   # Framework source — compiled to dist/ and published on npm
│   ├── authentication/    # Auth (JWT via jose) and Password (bcrypt) helpers
│   ├── database/          # Repository base class, BddParser, MySQL/Postgres adapters
│   ├── general/           # General-purpose utilities (Clone, Collection, SnakeToCamelParser)
│   ├── loggers/           # HttpResolver (HTTP responses) and Logger (file logging)
│   └── nodeExpress/       # Service, Middleware, Server, Controller, HTTP_METHODS
│       └── service-errors.config.ts
├── example/               # Reference application — not published, used for functional tests
│   ├── app/               # Express app wiring (App.ts, repositories, services, config)
│   └── tests/functional/  # Integration tests run via Docker Compose
├── bin/                   # CLI tool (pixelrest-new project generator)
├── docs/                  # Developer documentation (this tree)
└── dist/                  # Compiled output — generated by `npm run build`, gitignored
```

The published package is built exclusively from `src/`. The `example/` directory is a living showcase of how a consumer application should wire together all the framework primitives.

## Code conventions

### TypeScript — strict mode

- **No `any`** — use `unknown` and narrow with type guards when the shape is truly unknown.
- **No non-null assertions (`!`)** without an inline comment explaining why the value is guaranteed non-null at that point.
- TypeScript's `strict` flag is on; the compiler is the first line of defence.

### ES Modules

- The project uses `"type": "module"` — all imports use ESM syntax.
- **Always append `.js`** to local import paths, even when the source file is `.ts`. TypeScript resolves `.ts` → `.js` correctly at build time:

  ```ts
  // correct
  import Auth from '../../authentication/Auth/Auth.js';

  // wrong — will fail at runtime
  import Auth from '../../authentication/Auth/Auth';
  ```

### Naming

| Thing | Convention | Example |
|-------|-----------|---------|
| Classes and their source files | PascalCase | `UsersService`, `UsersService.ts` |
| Configuration / constant files | kebab-case | `service.config.ts`, `http-methods.config.ts` |
| Schema files | `<feature>.schema.ts` | `users.schema.ts` |
| Spec files | `<file>.spec.js` or `<file>.spec.ts` | `Service.spec.js` |

### Schema files (`*.schema.ts`)

- One schema file per feature, located next to its service file.
- Define Zod schemas for each request segment that needs validation (`body`, `params`, `query`).
- **Always export inferred types** with `z.infer<typeof schema>` — never duplicate types manually.
- Use `z.coerce.number()` for `params` and `query` fields that represent numbers, because URL segments are always strings.

  ```ts
  // users.schema.ts
  import { z } from 'zod';

  const getByIdSchema = z.object({
    id: z.coerce.number().int()   // coerce because URL params are strings
  });

  export const getByIdRouteSchema = { params: getByIdSchema };
  export type GetByIdParams = z.infer<typeof getByIdSchema>;
  ```

### Service files (`*.service.ts`)

- Extend `Service` from `pixelrest/service`.
- Declare `routesConfig: RouteConfig[]` as a class property.
- Call `this.initRoutes()` as the last statement in the constructor.
- Every `catch` block must delegate to `HttpResolver.handle()` — never write `res.status(500)` directly.

  ```ts
  constructor(tokenSecret: string) {
    super(tokenSecret);
    this.initRoutes();          // always last
  }
  ```

### Repository files (`*.repository.ts`)

- Extend `Repository` from `pixelrest/repository`.
- Pass `DbConnection` and `BddParser` to `super()` in the constructor.
- Use `~param` placeholders inside SQL strings — **never interpolate user-controlled data into SQL**.
- Every method must `catch` the error, call `Logger.handleSQLError(error)`, then `throw error`.

  ```ts
  // correct — parameterised
  await this.one('SELECT * FROM users WHERE id = ~id', { id });

  // wrong — SQL injection risk
  await this.one(`SELECT * FROM users WHERE id = ${id}`, {});
  ```

## Testing

### Unit tests

- Files: `*.spec.js` or `*.spec.ts`, co-located with the module they test (e.g. `Service.spec.js` next to `Service.ts`).
- Runner: Vitest.

```bash
npm test          # single run
npm run test:watch  # watch mode
```

### Functional tests

- Located in `example/tests/functional/`.
- Require MySQL and PostgreSQL containers (provided by Docker Compose).

```bash
npm run test:functional
```

This command starts the full Docker stack (DB + app), runs the tests, and tears everything down automatically.

**All unit and functional tests must pass before opening a pull request.**

## npm scripts reference

| Script | Command | Description |
|--------|---------|-------------|
| `build` | `tsc` | Compile `src/` → `dist/` |
| `start` | `tsx ./example/main.ts` | Start the example app |
| `dev` | `tsx watch ./example/main.ts` | Start the example app with hot reload |
| `prepare-file` | `tsx ./example/app/scripts/prepareDatabase.ts` | Seed / migrate the example database |
| `test` | `vitest run` | Run all unit tests once |
| `test:watch` | `vitest` | Run unit tests in watch mode |
| `lint` | `eslint .` | Lint the entire project |
| `docker:build` | `docker compose -f example/docker-compose.yml up --build` | Start the example app in Docker |
| `test:functional` | `docker compose -f example/docker-compose.test.yml …` | Run functional tests in Docker |

## Pull request checklist

Before submitting a pull request, verify that:

- [ ] `npm run build` passes with no TypeScript errors
- [ ] `npm test` passes (all unit tests green)
- [ ] `npm run test:functional` passes (all functional tests green)
- [ ] `npm run lint` passes with no errors
- [ ] No `any` introduced without justification
- [ ] All new schema files export inferred types via `z.infer<>`
- [ ] All new repository methods use `~param` placeholders, never string interpolation
- [ ] All new service `catch` blocks call `HttpResolver.handle()`, never `res.status(500)`
- [ ] All internal `docs/` links (if docs were updated) resolve correctly
- [ ] The PR description explains *why* the change is needed, not just *what* changed
